# 발표 리허설 — 가입 전 채팅부터 재로그인 로드맵 복원

> 상태: 구현·자동 검증·발표 계정 준비 완료 — 2026-09-14

## 1. 발표에서 증명할 한 문장

가입 전에는 짧은 채팅으로 고객을 붙잡고, 회원이 된 뒤에는 같은 분석을 장기 프로필과 개인
스윙 로드맵으로 이어서 재로그인 후에도 복원한다.

## 2. 선택한 실행 방식

### A. 사전 확인된 계정의 첫 로그인 — 추천

- Supabase Dashboard에서 이메일 확인이 끝난 발표 계정을 미리 한 개 만든다.
- 발표 전에는 이 계정으로 제품에 로그인하지 않는다.
- 발표 중 익명 채팅·분석 후 처음 로그인하면 현재 익명 owner가 회원 subject를 인계한다.
- 로그아웃 후 두 번째 로그인에서는 claim을 다시 시도하지 않고 회원 데이터를 복원한다.

비용은 가입 확인 자체를 무대에서 보여주지 못한다는 점이다. 대신 실제 Java API, 실제 DB,
실제 Supabase JWT, 실제 AI 분석과 복원 경로를 모두 사용한다.

### B. 발표 중 공개 회원가입 — 비추천

- 확인 메일 수신과 Supabase 이메일 rate limit에 의존한다.
- 2026-09-14 실제 점검에서 공개 가입은 `over_email_send_rate_limit`로 중단됐다.
- 발표 성공 여부를 제품 코드가 아닌 외부 이메일 상태가 결정하므로 기본 경로로 쓰지 않는다.

### C. 전체 mock — 비추천

- 화면 시연은 가장 안정적이지만 실제 owner claim, DB 저장과 JWT 검증을 증명하지 못한다.
- 자동 회귀 테스트에만 사용하고 발표 본 경로에는 사용하지 않는다.

## 3. 발표 한 바퀴

```text
로그아웃·빈 채팅
→ 7번 아이언 왼쪽 당김 질문
→ 짧은 후속 질문으로 고객 후킹
→ 실제 스윙 영상 첨부·분석
→ 사전 확인된 발표 계정으로 첫 로그인
→ 가입 전 대화·분석 owner claim
→ 장기 프로필 저장
→ 분석 결과를 개인 로드맵으로 저장
→ 로그아웃
→ 같은 계정으로 재로그인
→ 이전 대화·프로필·활성 로드맵 복원
```

### 화면 조작 순서

1. 헤더가 `채팅 · 가입 전 사용 가능`인지 확인한다.
2. `7번 아이언이 자꾸 왼쪽으로 가요. 오늘 연습에서 먼저 볼 한 가지만 알려줘.`를 보낸다.
3. 답변이 한 번에 한 질문만 하는지 확인한다.
4. `분석` → `사진·영상 첨부`에서 준비한 스윙 영상을 고른다.
5. `분석 시작`을 누른다. 분석 대기 시간에는 Java/Python 책임 경계를 설명한다.
6. 성공 카드에서 `내 로드맵으로 저장`을 눌러 가입·로그인 화면을 연다.
7. `이미 계정이 있어요 · 로그인`으로 전환하고 사전 확인된 발표 계정으로 로그인한다.
8. `가입 전 코칭 기록과 회원 상태를 이어받았습니다.`를 확인한다.
9. 메뉴 → `장기 프로필 편집`에서 표시 이름, 현재 성향, 목표 스윙을 저장한다.
10. 분석 카드의 `내 로드맵으로 저장`에서 목표를 확인하고 로드맵을 만든다.
11. 메뉴 → `로그아웃` 후 헤더가 비회원 상태로 바뀌는지 확인한다.
12. 같은 계정으로 다시 로그인한다.
13. `회원 세션과 저장된 코칭 상태를 복원했습니다.`를 확인한다.
14. 메뉴 → `내 스윙 로드맵`에서 이전 목표와 milestone이 같은지 확인한다.

## 4. 현재 측정한 시간과 상태

2026-09-14 로컬 실행 환경에서 확인했다.

| 경계 | 결과 | 측정값 |
|---|---|---:|
| FastAPI `/internal/health` | PASS | HTTP 200 |
| Spring `/health` | PASS | HTTP 200 |
| Vite `/` | PASS | HTTP 200 |
| 실제 익명 텍스트 채팅 | PASS | 10.2초 |
| 실제 MP4 영상 분석 | PASS | 41.4초 |
| 분석 상태 | PASS | `succeeded` |
| UI 회원 여정 자동 테스트 | PASS | 첫 claim 1회, 재로그인 추가 claim 0회 |
| 실제 재로그인 복원 | PASS | 프로필·대화·로드맵 ID 동일 |
| 공개 이메일 회원가입 | BLOCKED | Supabase 이메일 rate limit |

채팅과 영상 분석 시간은 Provider 상태에 따라 달라지므로 발표 시간 보장은 아니다.

## 5. 실패 판별과 전환 기준

| 관찰 | 판정 | 발표 중 행동 |
|---|---|---|
| 세 health 중 하나가 200이 아님 | 실행 경계 실패 | 시연을 시작하지 않는다. |
| 채팅이 20초 안에 답하지 않음 | Provider 지연 | 답변 대기 중 구조 설명으로 전환한다. |
| 분석 카드가 `분석 실패` | Provider 분석 실패 | 저장된 성공 분석과 복원 경로를 보여준다. |
| 로그인 뒤 `OWNER_CLAIM_CONFLICT` 문구 | 계정이 이미 다른 owner에 연결됨 | 해당 계정으로 첫-login claim 시연을 중단한다. |
| 로드맵 저장이 422 | 성공 분석 또는 교정 기준 부족 | 성공한 분석 카드를 다시 선택한다. |
| 재로그인 때 claim 요청 발생 | UI 회귀 | 발표 중단 후 회원 여정 테스트를 다시 실행한다. |

## 6. 발표 전 3분 점검

```powershell
Invoke-WebRequest http://127.0.0.1:8000/internal/health -UseBasicParsing
Invoke-WebRequest http://127.0.0.1:8080/health -UseBasicParsing
Invoke-WebRequest http://127.0.0.1:4173/ -UseBasicParsing
```

그리고 다음만 확인한다.

- 브라우저가 로그아웃 상태다.
- 발표용 영상이 로컬에 있다.
- 발표 계정은 Supabase에서 확인 완료됐고 아직 제품 owner와 연결되지 않았다.
- 이메일과 비밀번호는 `%TEMP%\swing-analyzer-presentation\presentation-account.json`에만 있다.
- 같은 발표 계정으로 첫-login claim을 미리 소비하지 않는다.

## 7. 다시 리허설할 때

첫 로그인 후 발표 계정은 owner에 영구 연결된다. 같은 계정으로 다음 리허설을 하면 재로그인
복원만 검증할 수 있고 익명 owner claim을 다시 증명할 수 없다. 전체 한 바퀴를 반복하려면
별도의 사전 확인 계정을 사용한다. 기존 회원 간 자동 병합이나 DB 수동 재지정은 하지 않는다.

## 8. 제외 범위

- Supabase 이메일 정책과 rate limit 변경
- 회원 간 데이터 자동 병합
- Provider 실패를 성공 결과로 가장하는 fallback
- 발표용 하드코딩 계정 또는 비밀번호
- Java/Python 책임 경계와 내부 API 계약 변경
